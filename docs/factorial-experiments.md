# 模型与上下文选择的两组对照实验

完成日期：2026-10-19。以下为当次实时模型结果，旧版回放、合成接口测试和此前单项目 Flash 运行均不混入。本次没有执行第三方项目代码，也未修改原始仓库、评测检查或预期输出。

## 设计与控制

采用 2×2 配置：DeepSeek `deepseek-flash` / 本地 Ollama `qwen2.5-coder:7b`，分别使用规则检索 / AI 选择上下文。三个项目每组合运行两次，合计 24 次分析、36 次正式模型请求；两个合成输入预热调用另外保存，不计入正式结果。

| 项目 | 固定 commit | 合格文件数 | 片段数 | 接触范围 |
| --- | --- | ---: | ---: | --- |
| TinyDB | `edff96aeb2616402e9489d46e90a592c05565621` | 30 | 261 | 此前接触过的开发项目 |
| Schedule | `82a43db1b938d8fdf60103bd41f329e06c8d3651` | 25 | 211 | 新冻结快照，不称独立留出 |
| Humanize | `785e5dcc0d0308ad0dff3f6cc0faa7085ad0375b` | 21 | 116 | 新冻结快照，不称独立留出 |

项目内容、摘要、候选集、模型、提示词、温度、生成上限和评阅标准均在正式调用前冻结。最终证据数组和选择摘要数组各最多 12000 字符；每次生成最多 2048 token，温度 0，socket 超时 180 秒。第二次重复交换策略顺序。本地种子为 17、29，Flash 无相同种子控制。

Ollama 0.40.3，Q4_K_M 7.6B，本机 RTX 4070 Laptop 8 GB；模型完全装入 GPU，运行上下文 8192、单并行。发行包、manifest 及主模型层均记录摘要，主模型层与已有缓存及官方 manifest 一致。临时模型目录与原缓存分开；完成后停止此次启动的服务并释放 GPU。

模型对照的主要控制组是规则检索：六对调用的输入片段逐字一致，分析指令相同；服务包装、模型架构、权重规模、量化和分词器仍不同，因此它比较的是这两套具体部署，不是 API 与 Ollama 传输接口的单独影响。AI 组分别由各自模型选择上下文，属于完整流程的额外观察。

## 当次结果

每行六次分析，对应三个项目各两次。时间为预热后模型请求耗时，AI 组包括额外选择请求，不包括项目读取时间；表中 token 是六次分析的累计值。

| 组合 | 建议数 | 助手核对为有支持 | 部分支持 | 无支持/不可判定 | 平均请求耗时 | 输入 token | 输出 token |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Flash + 规则检索 | 33 | 14 | 9 | 10 / 0 | 3.80 秒 | 23410 | 3684 |
| Flash + AI 选择 | 35 | 8 | 20 | 7 / 0 | 5.41 秒 | 45063 | 5046 |
| Qwen 7B / Ollama + 规则检索 | 36 | 0 | 10 | 26 / 0 | 19.07 秒 | 22532 | 3594 |
| Qwen 7B / Ollama + AI 选择 | 36 | 0 | 12 | 22 / 2 | 22.09 秒 | 33536 | 4197 |

全部 36 次正式请求正常返回，12 个成对记录的一致性审计均通过，没有选择失败回退。Ollama 的五次分析带有文字修改被拒绝的警告，分别因目标为 RST 或不是合格正文段落；这不是模型服务错误。四组均未导出被接受的文字补丁，不宣称完成教程修复。

在相同规则上下文下，Flash 平均请求耗时约为本地 7B 的五分之一，且产生更多能够对应具体原文事实的建议。例如它识别了 TinyDB 的 README 3.8+ 声明与包元数据 >=3.10 的差异；本地模型多次声称缺少 API/扩展文档，而引用的目录页本身已经包含相应入口。

AI 选择未在本次原文核对中提高有支持建议数。Flash 由 14 条降为 8 条，累计输入加输出 token 从 27094 增至 50109，平均请求时间增加约 42%；本地模型有支持建议数仍为 0，累计 token 从 26126 增至 37733，时间增加约 16%。相同最终字符上限不等于相同总 token/费用预算，不把这些数字称为等成本效果结论。

当前建议保持 Flash 为云端默认模型、规则检索为默认策略，AI 选择继续作为可选实验功能；这不是所有本地模型或其他项目上的一般排名。

## 原文核对标准及限制

正式调用前冻结四类标准：具体主张有原文支持且建议可操作为 supported；局部有帮助但范围或限定不完整为 partial；与原文矛盾或缺乏具体依据的缺失/不兼容判断为 unsupported；证据不足以核对主张为 unassessable。它们描述本次助手核对，不是独立人工准确率，也没有完整 gold 问题集可估计召回率。

140 条建议去除显式模型标签后打乱顺序，由助手查看冻结原文核对。并非严格盲测：TinyDB 的部分内容已见过，语言风格可能暴露模型，一条 Schedule 发布流程判断在首次汇总揭盲后，根据实际存在的 setup.py 更正。修订前评阅、汇总和更正原因均保留，没有为保留较好结果删除模型请求。

Flash 也有被原文反驳的判断，例如把 Schedule 的条件时区依赖误判为与可选 extra 冲突，或忽略 FAQ 旧版本示例后“或更高版本”的限定。模型生成的断言、建议数量和模型自行解释不作独立证据。只有三个项目，两次重复不增加独立项目数；没有学习效率实验、独立人工评阅或显著性结论。

## 复现与证据

持久证据包 `tutorial-factorial-20261019.tar.gz` 中的 `protocol.json` 为全局协议，`runtime.json` 为环境与摘要；`runs/项目/供应商/重复/` 保存子协议、实现归档、输入快照及两种策略的原始请求/响应、报告和审计；`blind-review.json`、`quality-review.json`、`review-revisions.json` 保存评阅及修订；`results.json`、`report.html` 保存逐次和汇总结果。第三方源码随独立证据包保留并携带许可证，模型权重未纳入证据包或源码补丁。逐文件摘要及归档复核见 [交付验证](delivery-validation.md)，资源与许可见 [resources.md](resources.md)。

复现需自行运行对应 Ollama 模型并配置 `DEEPSEEK_API_KEY`，输出目录必须全新且位于输入项目之外：

```sh
python3 scripts/run_tutorial_factorial.py freeze /tmp/new-tutorial-study
python3 scripts/run_tutorial_factorial.py run /tmp/new-tutorial-study
```

首次 freeze 会把 HEAD 解析为实际 commit，后续必须以保存的协议为准。上述命令不会自动重试或覆盖已存在的运行，不能用重跑覆盖本次记录。新 HEAD、服务模型更新、缓存状态或硬件变化均可能改变结果。
