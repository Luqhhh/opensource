# 语义验证与方法改进 v2

本轮分别保存加强语义检查后的开发实验和新的项目留出实验。旧 [v1 冻结结果](../real-projects-20261013/README.md) 与原案例保持原样；不能用新检查追改旧分数。这里的“通过”仍指预先声明的有限检查及补丁应用复查通过，不等于人工确认的一般语义正确率。

**结果：语义检查增强并拒绝了输出看似正确的错误候选；新方法改善了已见 TinyDB 默认表案例。新留出集五组均为 0/12，未证明修复效果提升或反馈收益。** 新无反馈方法在留出集少用 40.32% 输入 token，但不能换算成更低的成功修复成本。两轮开发 104 次、留出 180 次，共 284 次真实请求完整保留。

## 检查覆盖与工程证据

[开发集](../../../benchmarks/semantic_v2/development/README.md) 共 6 个失败、3 个健康案例，来自已观察过的 TinyDB、more-itertools、MarkupSafe 迁移。除原显示示例外，新增明确标注的可复用绑定契约，属于评价者编写的扩展，不能说成全部机械提取的上游例子或新留出数据。

- MarkupSafe：区分字符串转换与 HTML 转义；覆盖普通、空、Unicode、含 HTML 的字符串、字符串子类、Markup 的类型与对象身份、数值、布尔值、None，以及自定义 `__str__`/`__html__`。
- TinyDB：默认表与命名表的作用域、多条记录、空表、缺失表、重复调用、ID 重置、表重建后的查询结果和磁盘持久化。
- collate：可复用调用绑定、`key`/`reverse` 组合、重复值与相同键顺序、Unicode、空输入、一次性迭代器、构造惰性和无限输入的有限前缀。

同一检查在旧版库下 **9/9 通过**，目标版本复现 **6 失败、3 健康**，参考修复全部通过。另有 **9 个格式合法的错误候选全部被外部检查拒绝**，其中 **8 个的 stdout 仍与示例一致**。[工程验证](../../../benchmarks/semantic_v2/development/evidence/validation-02/validation.json) 不调用模型，不计入实时模型成绩；负例覆盖也不是一般误修复率。

检查仍在同一沙箱进程中的后续阶段执行。它们增强对普通错误候选的辨别，不能抵御任意恶意程序篡改进程状态，也没有覆盖所有可能输入、性能或并发行为。

独立复审还发现一个保留的检查盲点：默认表例先查询、再插入、再清空，插入操作本身已使查询缓存失效，因此不能单独证明清空操作会使已填充的查询缓存失效。记录这一限制，不修改已冻结检查或重算旧分数。

## 固定的五组比较

| 组别 | 源码与提示词 | 后续请求 |
|---|---|---|
| legacy_source | v1 提示词和 12000 字符检索 | 独立采样 |
| legacy_feedback | 与 legacy_source 相同 | 普通执行反馈 |
| source_v2 | v2 检索和通用契约提示词，总计 6000 字符 | 独立采样 |
| generic_feedback_v2 | 与 source_v2 相同 | 普通执行反馈 |
| feedback_v2 | 与 source_v2 相同 | 普通反馈加宿主分类 |

分类来自执行阶段、完成标记和 stdout 比较，包括异常、行为检查失败、输出不符、超时等固定类别。具体外部断言和预期值不进入请求；首轮三个 v2 条件获得相同 payload，分类只在后续历史中出现。因此 source_v2 与 generic_feedback_v2 比较历史反馈，后者与 feedback_v2 比较额外分类；旧方法与新方法的差异同时包含检索、提示词和后续加入的标准库语料，不能单独归因于其中一项。

统一使用 `qwen2.5-coder:7b` Q4_K_M，模型摘要 `dae161e27b0e90dd1856c8bb3209201fd6736d8eb66298e75ed87571486f4364`、Ollama 0.40.3、temperature 0.2、上下文 8192、每次最多 1024 个生成 token、每例最多 3 次请求、超时 180 秒。各组首次通过即停，无效 JSON、格式拒绝和失败均计调用及成本。固定的是最大调用与输出预算，实际输入 token 不相等。

## 开发迭代 01：完整保留的负结果

[协议与实现](../semantic-v2-development-20261013/protocol.json) 在本轮调用前冻结，seed=17。15 个单元、52 次请求全部保留。[独立审计](../semantic-v2-development-20261013/independent-audit.json) 核对首轮配对、原始响应、成本、补丁和复查。

| 组别 | 首轮 / 预算内通过 | 请求 | 输入 token | 输出 token |
|---|---|---:|---:|---:|
| legacy_source | 3/6 / 4/6 | 11 | 49,476 | 2,896 |
| legacy_feedback | 3/6 / 4/6 | 11 | 52,445 | 1,912 |
| source_v2 | 4/6 / 4/6 | 10 | 28,003 | 1,856 |
| generic_feedback_v2 | 4/6 / 4/6 | 10 | 30,240 | 1,721 |
| feedback_v2 | 4/6 / 4/6 | 10 | 30,127 | 1,619 |

新方法修复了 TinyDB 默认表，却未修好通用转换契约；旧方法两组第二轮通过该转换契约。collate 五组均失败。源码里虽包含正确转换接口，但无关私有包装器仍干扰生成；collate 候选则反复误选不等价的库内函数。反馈没有增加预算内通过数。1 次响应达到 1024 个生成 token 上限，完整响应和失败仍保留；全部响应的最大输入加输出计数为 6128，低于上下文 8192。这些是服务返回计数核对，不是独立 tokenizer 证明。

因此进行第二次开发迭代：仅对原始缺失导入与项目包匹配的情形检索固定的公开标准库接口语料；过滤未被任务调用或错误明确引用的私有实现。保持同一套开发输入与检查，并保留本轮结果。

## 开发迭代 02：最终方法及仍未解决的问题

固定语料来自官方 CPython 3.10.12 的 153 个公开平面 Python 模块，按统一规则提取 999 个顶层公开函数的签名/docstring，原文、摘要、生成器及许可均保存。没有按案例手工写入替代函数。缺失项目导入触发时分配项目 4000、标准库 2000 字符；否则项目最多 6000。标准库候选最多 3 个，并要求函数名与额外任务词同时匹配。它不覆盖类、子包、C 内置实现，仍可能检索到不等价 API。

[第二次开发实验](../semantic-v2-development-02-20261013/protocol.json) 同样完成 15 单元、52 请求；[独立审计](../semantic-v2-development-02-20261013/independent-audit.json) 通过。两次开发共 104 次请求全部保留，不能只展示最终一次或把两轮视作独立数据。

| 组别 | 首轮 / 预算内通过 | 请求 | 输入 token | 输出 token | 请求累计秒 |
|---|---|---:|---:|---:|---:|
| legacy_source | 3/6 / 4/6 | 11 | 49,476 | 2,896 | 102.6515 |
| legacy_feedback | 3/6 / 4/6 | 11 | 52,445 | 1,912 | 66.3379 |
| source_v2 | 4/6 / 4/6 | 10 | 24,844 | 1,723 | 58.3376 |
| generic_feedback_v2 | 4/6 / 4/6 | 10 | 26,263 | 1,707 | 52.5915 |
| feedback_v2 | 4/6 / 4/6 | 10 | 26,362 | 1,710 | 51.5171 |

新无反馈方法与旧无反馈方法都通过 4/6，但对应的案例不同；输入 token 减少 49.79%，总 token 减少 49.27%。这是已见开发集单种子的成本观察，不是泛化结果，也不能据请求耗时声称速度提升。所有组各有 3 个健康对照保持通过且不调用模型。

- **TinyDB 默认表：** 新三组均首轮通过，旧两组仍失败。新检索保留默认表属性及委托关系，有助于避免把默认表清空误写为删除错误表名；这也是提示词与检索合并变化，未隔离单项因果。
- **collate 仍未修复：** 新三组都找到了 `heapq.merge`，但没有保留公开要求的 `collate` callable，三次均被行为检查拒绝。检索命中不是修复成功；反馈也没有纠正这个问题。
- **MarkupSafe 通用转换仍失败：** 新三组生成函数定义，触发当前直线代码守卫；不能将结构拒绝说成已经执行了通用语义测试。旧两组第二次通过。原固定安全文本显示例各组仍通过，只支持该有限显示契约。
- **分类反馈未带来净收益：** 与普通反馈相比输入多 99、输出多 3 个 token，通过数相同；与无反馈相比也没有增加通过数。更细类别仍未给模型提供足够可执行的纠错依据。

## 新项目留出与冻结顺序

[独立采集集](../../../benchmarks/semantic_v2/holdout/README.md) 包含 Mistune 0.8.4→3.1.3 的 HTML 渲染／选项迁移，以及 Werkzeug 2.2.3→3.0.6 的路径读取／弹出迁移，合计 **4 个失败、2 个健康**。MarkupSafe 2.1.5 和 typing_extensions 4.12.2 仅是固定运行源码依赖。旧版同检查 6/6 通过，目标 4 失败／2 健康，参考补丁复查 6/6 通过，4 个错误候选全部被外部检查拒绝。上述工程控制均为 0 次模型调用。

采集者先封存 266 个输入文件，清单 SHA-256 为 `48557123a7453b5e8a899f7531e3b4cc4773ce1e158136ba0aa974cbe6d485ac`。实现负责人锁定最终 revision 2 方法后才获知具体项目和题目；[方法锁](method-lock.json) SHA-256 为 `76087371cf7e09eee4d03c03ce9308597a394d5a1f1dcabdc43098bbd3586fe2`。锁定发生在开发迭代 02 完成之前，之后没有按开发或留出输出再改方法。全部封存文件的 SHA 与字节数复核一致，再保存 [留出协议](../semantic-v2-holdout-20261013/protocol.json)，然后才调用模型。

这是独立采集、未用于本次方法优化的历史案例，**不是双盲或随机抽样**。采集者在选题之后、完善检查之前，为查接口意外读到了通用提示词增补和分类开头，已在 [采集边界说明](../../../benchmarks/semantic_v2/holdout/COLLECTION-BOUNDARY-NOTE.md) 披露；没有查看模型输出或检索实现。不能保证公开文本未进入模型预训练。语义检查仍有限，参考 lambda 迁移仅用于演示有限契约，不作为生产代码风格建议。

## 留出完整结果与成本

30 个项目／组别／种子单元全部完成，最终模型摘要与冻结输入核对通过；[独立审计](../semantic-v2-holdout-20261013/independent-audit.json) 核对 30 个单元、999 条标准库原文索引及 24 组首轮请求，原始成本与 [summary.json](../semantic-v2-holdout-20261013/summary.json) 一致。失败分母为 **4 个案例 × 3 个种子 = 12 次案例运行**，并非 12 个独立缺陷。

| 组别 | 首轮 / 预算内通过 | 请求 | 输入 token | 输出 token | 请求累计秒 |
|---|---|---:|---:|---:|---:|
| legacy_source | 0/12 / 0/12 | 36 | 160,488 | 4,381 | 157.2636 |
| legacy_feedback | 0/12 / 0/12 | 36 | 167,584 | 4,378 | 168.0013 |
| source_v2 | 0/12 / 0/12 | 36 | 95,778 | 4,461 | 154.1977 |
| generic_feedback_v2 | 0/12 / 0/12 | 36 | 103,806 | 4,542 | 157.7971 |
| feedback_v2 | 0/12 / 0/12 | 36 | 105,411 | 4,624 | 164.1708 |

每组另有 2 个健康案例 × 3 个种子的 **6/6 保持通过**，不调用模型。全部 180 次失败候选均执行后记为 `repair_failed`，没有补入人工参考候选、删掉失败或事后放宽检查。每个不同失败案例在所有组和种子中都未获通过，因此**每个成功修复的成本未定义**。

source_v2 的输入 token 比 legacy_source 少 40.32%；普通反馈比 source_v2 增加 8028 输入、81 输出 token；分类反馈又比普通反馈增加 1605 输入、82 输出 token，通过数均没有增加。这只说明当前固定预算下的实际 token 使用量，不能宣称质量提升、总体效率领先、费用或能耗降低。

实际失败包括：Mistune 对可复用 HTML 返回值、构造器参数、转义／硬换行与显示约束处理不当；Werkzeug 将路径弹出／查看近似替换成 `get_path_info`，未保留完整的状态修改、切分与可复用绑定语义。逐次状态、候选和重复记录见 [case-analysis.json](../semantic-v2-holdout-20261013/case-analysis.json)；不能把从导入错误变为行为检查失败算作成功。

24 组相同首轮 payload 中，10 组原始 JSON 文本不同，仅 1 组候选代码不同，首轮结果均失败；固定 seed 是请求控制，不保证该 Ollama/GPU 环境逐字节确定。三组 v2 首轮反馈尚未发生，首轮差异不能归因于反馈。留出响应全部 `done_reason=stop`，最大输入＋输出计数 5559，低于 8192；仍只是服务返回计数核对。实验期间观察到其他 GPU 工作负载，[运行条件记录](runtime-conditions.json) 已披露，因此请求耗时不作为隔离吞吐或速度提升证据。
